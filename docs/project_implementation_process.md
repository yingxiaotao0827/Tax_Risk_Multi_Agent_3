# 税务风险智能诊断分析系统：规划与实现过程

## 1. 项目目标拆解

本项目的目标不是做一个简单的“税务法规问答机器人”，而是实现一个可以模拟税务专家工作流的智能诊断系统。系统需要基于企业财报、发票流向、税务申报数据和法规库，自动识别潜在税务风险，并输出可追溯、可复核的《企业税务健康体检报告》。

核心目标拆成四类：

- 风险发现：识别进项异常、收入发票差异、税负率异常等问题。
- 证据补全：通过 SQL、财务指标、法规检索形成结构化证据链。
- 交叉验证：避免单一指标直接下结论，要求数据、规则、结论互相支撑。
- 复核兜底：当证据不足、结论冲突或置信度不足时进入人工复核。

## 2. 时间规划合理性验证

项目周期设定为 `2025.04 - 2025.08`。在实现前需要先判断技术是否已经成熟，否则简历项目容易被面试官追问“当时这个技术能不能用”。

验证结论：

- Qwen2.5 系列于 2024-09 发布，2025.04 时已经可以作为私有化部署主模型使用。
- Qwen2.5-14B-Instruct 在效果和资源成本之间比较平衡，适合中型企业本地部署或私有云部署。
- LangChain v0.3 于 2024-09 发布，2025.04 时 Tool、Agent、Runnable、结构化输出等能力已经适合工程化使用。
- Milvus 2.5 于 2024-12 发布，2025.04 时 2.5.x 已有稳定补丁版本，适合法规库向量检索和混合检索。

因此，在 `2025.04 - 2025.08` 内完成一个生产可用的税务风险诊断系统是合理的。

## 3. 技术选型

### 3.1 主模型

主模型选择 `Qwen2.5-14B-Instruct`。

选择理由：

- 中文能力较强，适合税务、财务、法规等中文专业文本。
- 14B 规模在本地化部署成本和推理效果之间较均衡。
- 支持指令跟随、结构化输出、工具调用提示，适合 Agent 场景。
- 可以通过 vLLM、Ollama 或 OpenAI-compatible API 接入应用系统。

### 3.2 Agent 框架

选择 LangChain。

选择理由：

- 对 Tool、Retriever、LLM、Prompt、Runnable 有完整抽象。
- 便于把 SQL 查询、指标计算、法规检索封装成工具。
- 适合快速搭建 ReAct 风格的推理链路。
- 对 OpenAI-compatible 模型接入友好，便于替换 Qwen 推理服务。

### 3.3 向量数据库

选择 Milvus。

选择理由：

- 适合企业法规库、政策文件、历史案例的语义检索。
- 2.5 版本已经支持更强的混合检索能力。
- 在数据规模增长后比本地文件检索更容易扩展。

### 3.4 服务框架

选择 FastAPI。

选择理由：

- 适合提供诊断 API、复核队列 API 和健康检查 API。
- 与 Pydantic 结构化数据模型天然配合。
- 便于后续接前端、权限系统、任务队列和审计日志。

## 4. 总体架构设计

系统分为五层：

- 数据层：企业财报、发票、申报表、法规文档。
- 工具层：只读 SQL、财务指标计算、法规检索、证据链构建。
- Agent 层：稽查主 Agent、监督审核 Agent。
- 服务层：诊断编排、报告生成、人工复核队列。
- 接口层：FastAPI、CLI、Markdown 报告输出。

关键设计点：

- 主 Agent 不直接“编答案”，而是先调用工具取证。
- 所有风险结论必须绑定证据、指标和法规引用。
- 监督 Agent 对每个结论做质量门禁。
- 低置信度、证据缺失、工具超预算等情况自动降级到人工复核。

## 5. 数据建模

演示系统中先使用 SQLite 表达结构化业务数据，生产环境可以替换为 PostgreSQL、MySQL 或数仓。

主要数据表：

- `monthly_tax`：企业月度收入、销项税、进项税、成本。
- `invoices`：企业发票流向、交易对手、金额、税额。

主要法规数据：

- `vat_input.md`：进项税额异常抵扣风险规则。
- `revenue_invoice.md`：收入确认与销项发票一致性风险规则。

核心结构化对象：

- `Evidence`：证据项。
- `RiskFinding`：风险发现。
- `SupervisorResult`：监督审核结果。
- `DiagnosticReport`：最终诊断报告。

## 6. 工具链设计

### 6.1 只读 SQL 工具

只读 SQL 工具用于查询企业财报、发票流向和税务申报数据。

设计约束：

- 只允许执行 `SELECT`。
- 拦截 `INSERT`、`UPDATE`、`DELETE`、`DROP`、`ALTER` 等危险语句。
- 所有查询结果转换成结构化字典，便于 Agent 使用。

### 6.2 财务指标工具

指标工具用于把原始数据转成可判断的风险特征。

当前实现了三个指标：

- 增值税税负率：`(销项税额 - 进项税额) / 营业收入`
- 进项税额增长率：`(本年进项税额 - 上年进项税额) / 上年进项税额`
- 收入发票差异率：`(销项发票金额 - 营业收入) / 营业收入`

### 6.3 法规检索工具

法规检索工具用于给风险结论补充政策依据。

当前本地演示使用轻量文本检索，生产环境可通过 Milvus 构建法规向量索引。

## 7. 双 Agent 机制

### 7.1 稽查主 Agent

主 Agent 的职责是模拟税务稽查专家。

工作方式：

1. 根据企业编号和年度读取财税数据。
2. 调用财务指标工具计算风险指标。
3. 根据阈值提出风险假设。
4. 调用法规检索工具补充政策依据。
5. 生成结构化风险发现。

当前规则示例：

- 如果进项税额增长率超过 35%，同时增值税税负率低于 2.5%，触发“进项税额异常增长且税负率偏低”。
- 如果销项发票金额与营业收入差异超过 8%，触发“确认收入与销项发票金额背离”。

### 7.2 监督审核 Agent

监督 Agent 的职责是控制质量，而不是重新生成报告。

审核维度：

- 是否存在证据链。
- 高中风险结论是否有法规引用。
- 置信度是否达到出具阈值。
- 高风险结论是否具备更高可信度。
- 是否出现工具预算超限、数据缺失或逻辑冲突。

如果审核分低于阈值，或者存在异常警告，系统会把报告标记为 `pending_human`，进入人工复核队列。

## 8. Human-in-the-Loop 设计

人工复核不是附加功能，而是税务场景的必要安全机制。

进入人工复核的典型场景：

- 关键财务数据缺失。
- 工具调用超过预算。
- 监督审核分低于阈值。
- 结论置信度不足。
- 风险结论缺少法规引用。
- 多个工具返回的结果互相冲突。

当前实现中，待复核报告会写入 `tax_risk_ai/data/review_queue.json`。生产环境中可以替换为数据库表、工单系统或审批流。

## 9. 报告生成

报告输出包含：

- 报告编号。
- 企业编号。
- 诊断年度。
- 复核状态。
- 监督评分。
- 风险总结。
- 每项风险的编码、等级、置信度、判断理由、法规引用和整改建议。
- 可视化图表数据。

当前系统支持 Markdown 报告和 API JSON 输出。

## 10. API 设计

当前提供三个基础接口：

- `GET /health`：健康检查。
- `POST /diagnostics/run`：发起诊断。
- `GET /reviews/pending`：查看待人工复核报告。

示例请求：

```json
{
  "company_id": "C001",
  "year": 2024
}
```

## 11. 实现步骤

### 第一步：创建工程结构

创建 `tax_risk_ai` 项目目录，划分 `agents`、`tools`、`services`、`api`、`data`、`scripts`、`tests`、`docs` 等模块。

### 第二步：准备环境

编写 `environment.yml`，声明 Python、FastAPI、LangChain、Milvus、Pydantic、SQLAlchemy、pytest 等依赖。

### 第三步：准备数据

创建演示 CSV 数据，包括企业月度税务数据和发票数据。编写初始化脚本，将 CSV 导入 SQLite。

### 第四步：实现工具层

实现只读 SQL 工具、财务指标工具和法规检索工具。

### 第五步：实现 Agent 层

实现稽查主 Agent 和监督审核 Agent，并让主 Agent 输出结构化风险发现。

### 第六步：实现编排层

实现 `DiagnosticOrchestrator`，串联主 Agent、监督 Agent、报告生成和人工复核队列。

### 第七步：实现 API 层

使用 FastAPI 暴露诊断接口、健康检查接口和人工复核接口。

### 第八步：实现报告输出

将结构化诊断结果转换为 Markdown 报告，并保留 JSON 结构，方便前端展示。

### 第九步：加入 Milvus 支持

编写 `build_rule_index.py`，用于把法规文档写入 Milvus collection。演示环境可使用本地检索 fallback，生产环境启用 Milvus。

### 第十步：验证系统

运行初始化脚本、诊断脚本和单元测试，确认系统可执行。

验证命令：

```bash
python3 tax_risk_ai/scripts/init_demo_data.py
python3 tax_risk_ai/scripts/run_diagnosis.py --company-id C001 --year 2024
python3 -m pytest tax_risk_ai/tests
```

## 12. 生产化扩展方向

后续可扩展：

- 将 SQLite 替换为 PostgreSQL 或数仓。
- 将本地法规检索替换为 Milvus 混合检索。
- 接入 vLLM 部署的 Qwen2.5-14B-Instruct。
- 加入 LangSmith 或自研 tracing 做 Agent 可观测性。
- 加入任务队列，支持批量企业异步诊断。
- 加入权限控制和审计日志。
- 加入人工复核前端和审批流。
- 建立六类税务任务评测集，持续评估准确率和误报率。

## 13. 面试讲法

可以这样总结：

> 我做这个项目时，核心不是让大模型直接生成税务结论，而是把税务专家的诊断过程拆成 Agent 工作流。主 Agent 负责提出风险假设并调用只读 SQL、财务指标、法规检索工具补证；监督 Agent 负责检查证据链、法规引用和结论一致性。系统对低置信度、数据缺失、工具超预算等情况自动降级到人工复核，从架构上降低错误结论直接出具的风险。最终报告里的每个风险点都能追溯到指标、数据和法规依据。
